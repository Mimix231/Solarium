# 07 — 12 Mega-Phases, One Complete Phase per Round

These are **implementation plans**. Source review confirms some existing foundations; no phase described here is claimed complete by this pack.

| Round | Mega-phase | Tangible result | Why this order |
| --- | --- | --- | --- |
| **01** | One-file-per-block registry + canon preservation | 26 existing blocks split into category files, generated verified registry, honest catalog counts | Stable IDs and no giant TS registry |
| **02** | Dream glass workbench + actual terminal build stream | Centered overlay over Chat, xterm-like live events, Monaco `+`/`−` diff, always-visible app preview | Deliver desired user experience early, using existing pipeline |
| **03** | Universal typed graph v2 | Typed ports/nodes/edges, validation, migration and v1 compatibility | Blocks can compose beyond existing app schema |
| **04** | Block execution SDK and sandbox | Lazy executable adapters, scheduling, permissions, tracing and cancellation | Blocks do actual work with dependable contracts |
| **05** | 10K-per-category warehouse scaling | Hierarchical 35-category search across 350K **synthetic/draft capacity**, not 350K real blocks | Discover a handful of useful capabilities in a huge index |
| **06** | Professional UI, functions, variables, styling and quality | Library-backed MUI apps, theme tokens, layout, state, audits, actual target renderers | Professional apps rather than browser-default UI |
| **07** | Spark-driven assembly | Dona discovers, inspects, composes, checks, runs and repairs with real tool outputs | Small LLM receives only focused contracts |
| **08** | Evidence-driven web research | Search result → follow-up block → verification → cited evidence with budgets | Intelligent multi-hop research rather than shallow search |
| **09** | Native/web independent export | Accurate dependency bundling, target validators, actual standalone outputs | Users own functional exported software |
| **10** | Glitch hybrid development | Block↔source navigation, source ownership, custom code adapters | Advanced editing without false code-to-block promises |
| **11** | Separate LeonisMaker game adapter | Dedicated game categories and scene/runtime bridge with tests | Games use game engines, not generic MUI forms |
| **12** | Hardened ecosystem and block evolution | Signed/reviewed extensions, migration, telemetry, performance, promotion | Reliable open source growth |

**Each round is large but finite.** Finish complete functionality and tests for its declared result. Do not interpret one round as implementing 10,000 production blocks; scale is a registry/catalog objective and verified blocks grow incrementally.

## Canon continuity

Initial source-of-truth reviewed: `Solarium[Bak].zip` dated 11 November 2026. Before starting each implementation round, ask for or use the **newest** project source if more changes have been made. Do not roll back newer Solarium features. The code ZIP was inspected but this plan did **not** run full npm, Rust, Windows or native app verification; actual implementation must perform those checks.

## Non-negotiable decisions accepted from user

1. **No separate Spica workspace tab**; keep it in Solarium conversation with a centered overlay.
2. **Terminal build process** with real events and logs; **dreamy professional glass** styled consistently with Solarium.
3. **Side-by-side red deletion / green addition code diff**, and an interactive app preview visible through the overlay.
4. **Exactly one canonical block definition per source file**, stored in a proper category/subcategory.
5. **Registered, validated blocks** with no phantom executable counts, no hand-maintained monolith.
6. **MUI/professional component packages** for generated UI apps; generated app dependencies truly include them.
7. **Separate game block families and renderers**, sharing only appropriate contracts/logic.
8. Preserve existing app graphs, user data, agent inference behavior, source ownership and permission safeguards.
